# Dragonize — branding and legal notes (2026-11-05)

The app ships as **Dragonize** (`Dragonize-x86_64.AppImage`, binary `dragonize`),
an unofficial tool for M801-RGB compatible mice (USB 04d9:fc58). English is the
default language.

- Every image the UI draws is original artwork generated by
  `tools/make_brand.py` into `assets/brand/` (frame, dialogs, buttons, sliders,
  icons, emblem, wordmark, mouse illustration). Layout and sizes follow the
  original program so the look and feel stay close.
- Logo: the owner's Dragonize logo (`assets/brand-src/dragonize.png`), cut into
  `dragon.png` + `wordmark.png` and placed in the header, emblem, icon.
- Exception, by the owner's informed decision (2026-11-05): the General tab
  keeps the manufacturer's product photo (`assets/vendor/mouse-layout-front.png`,
  their copyrighted photo, shows their logo). Removing that file makes
  make_brand.py fall back to the original illustration.
- No other vendor artwork, logo, product name ("Sniper") or web address is
  embedded; the vendor-derived pieces used during development were moved to
  `reference/vendor-assets/` (research material, not shipped).
- The model name M801-RGB appears only to state compatibility, next to the
  disclaimer "Unofficial tool, not affiliated with the mouse manufacturer".
- Bundled fonts: Wine Tahoma (LGPL), Noto Sans CJK TC subset (OFL).
- Other models (2026-11-05): same informed decision for their product photos
  (`assets/vendor/mice/*.png`, from RDCfg.exe's skin, margins cropped and
  scaled to the 189x270 photo box). Model names are RDCfg's own, shown to
  state compatibility; retail names added only for the M711 (COBRA) and the
  M801 entry.

The sections below describe the original program that was studied.

# Other models (RDCfg.exe, 2026-11-05)

Redragon's universal driver "REDRAGON Gaming Mouse.exe" (RDCfg.exe, Qt)
configures 52 Holtek mice (04d9:fc2a..fc75). Its device layer (0x456c40-
0x45d5c0) uses exactly the M801 protocol: `02 f5` session, `f3` writes in
16/64-byte feature reports, `02 f1 02 MASK` commits, profile bases
0x40/0x100/0x1b0/0x260/0x310, DPI stages at base+4+6i, buttons from
base+0x42, polling 0x32, lighting 0x449+8p, macros 0x478+200*slot. Per model
only these differ; all were obtained by running RDCfg's own functions per
product name in Ghidra's emulator (`tools/re/rdcfg/`, README there), then
generated into `src/models_data.rs`:

- identity: PID + bcdDevice range (RDCfg Config.ini `Mouse_List`; the app reads
  bcdDevice from sysfs). Unknown revisions fall back to the first entry of
  the PID; for fc58 that is the M801.
- button slots and addresses (FUN_0045d5c0 -> FUN_0045c570), 6-23 buttons plus
  wheel up/down; the general page scrolls when there are more than 11 rows.
- button markers on the product photo (FUN_00406780).
- DPI: sensor per model (FUN_004314d0, 10 sensors), slider range per model
  (FUN_00436d40), index -> CPI (FUN_00432150) and index -> register
  (FUN_00457b30) emulated for every index. Two indices that RDCfg encodes to
  the same register (2805: 15900/16000) are offered once.
- lighting variant (FUN_00431a30): 3 = the M801's 8 modes (the Cobra too);
  0-2 = six modes (no trail/reactive, FUN_00456d90 table
  (2,1)(3,1)(1,1)(5,1)(4,1)(0,0)); 4 and the 2850 = zone lighting, not
  decoded: the lighting tab says so and the device bytes are never written.

Cross-checks against the verified M801: RDCfg's entry 04d9:fc58 rev 2.xx
("M912-RGB") has the M801's 11 button addresses and its sensor table equals
the M801's hid.exe DPI table for every index (unit test
`m801_entry_is_the_verified_layout`); the "2805" (same PID, rev 3.xx) is the
same shell with another sensor. The user's M801 revision still has to be
read (`dragonize --diagnose`) to confirm it is rev 2.xx.

Several mice: `device::scan()` lists every plugged supported mouse (vendor
page 0xffa0 interface); one is opened directly, several open a selection
window (photo, name, USB port); clicking the model name in the header
switches later. Profiles of other models live in
`~/.config/m801-rgb/models/<key>/`; the M801 keeps its original location.
The udev rule lists every supported PID (04d9 alone would match unrelated
Holtek devices). CLI: `--list-models`, `--model KEY`, `--usb PORT`.

Not verified on hardware: everything specific to models other than the M801
(no such mouse was available); the protocol and encoders are RDCfg's own.

# M801-RGB Mechanics

Behaviour and layout of the original configuration tool (`ldcfg.exe`,
MFC, from the Inno Setup 5.5.7 installer `M801-RGB setup.exe`), as reproduced
by this port. Values in `mechanics.json` carry their source.

## How the ground truth was obtained

1. `innoextract` unpacks the installer: `app/ldcfg.exe`, skin images under
   `app/images/0409/`, strings in `app/images/{0409,tc,sc}/strings/*.ini`,
   default profiles `userdocs/.../RSProfile1-5.pfd`, `MacroDB/MacroSet.MSDB`.
2. `ldcfg.exe` was run under Wine in an isolated prefix with font linking
   Tahoma/Segoe UI -> Microsoft JhengHei (what a Traditional Chinese Windows
   does). Every screen was captured with `import` and driven with a Win32
   injector (`tools/re/inj.c`; `pclick X Y b` = BM_CLICK works reliably).
   Captures: `../reference/original/`.
3. Widget positions were measured on the captures (`tools/re/comp.py`,
   `runs.py`); scaled skin images were fitted (`fit.py`, `fitframe.py`).

The `0409` ("English") string folder actually holds Traditional Chinese, so
the original UI is Chinese on every system locale.

## Rendering

- The window is the 795x625 `cfgMainback.png` with transparent corners. The
  vendor image had a stray 1px bar on top of the "M" of "GAMING MOUSE"; it is
  retouched by `tools/patch_background.py` (on request; the original showed it).
- Popup menu labels keep two spaces of clearance before a submenu arrow and are
  shortened with "..." when they do not fit (long translations).
- Most controls are GDI+ anti-aliased shapes, not bitmaps. Their backgrounds
  are cut from the captures by `tools/extract_skin.py` into `assets/skin/`
  (text erased with the flat fill), so edges match pixel for pixel.
- Stretched bitmaps: mouse picture = `mouse-layout-front.png` nearest-neighbour
  to 189x270 at (102,201); dialog frames = `dlg.png` box-filtered to 478x292
  (small dialogs) and bilinear to 757x582 (macro manager).
- Text: Latin glyphs from Tahoma (Wine's LGPL clone is bundled), CJK glyphs from
  Microsoft JhengHei when installed, else the bundled Noto Sans CJK TC subset.
  Each control has its own Latin/CJK size pair (font linking), measured on the
  captures; all glyphs share the base font baseline.
- `--screenshot FILE --scene NAME` renders without a window; compare with
  `tools/re/cmp.py`. Identical pixels vs. the original captures (MS JhengHei
  installed): main 93%, DPI 98%, lighting 94-97%, info 96%, dialogs 95%,
  macro manager 92%. The rest is text anti-aliasing (GDI hinting vs. ab_glyph).

## DPI

- Five stages, each enable-able (at least one stays on). Range 200-12400 CPI.
  The original toggled a stage with a check mark inside its "DPIn" title; on
  request the port draws the title without it (`dpi_label`, mirrored left half)
  and toggles with a right-click on the title; disabled stages are dimmed.
  Left-click selects the current stage (檔位); only the current stage shows the
  check mark (`check_mask`, cut from the original), two spaces after the name.
- Info page: language row and a tribute to the port's author, Vortron
  (circular avatar `assets/vortron.png` from `tools/make_avatar.py`, string
  `skins.ini [General] 92`). Fonts subset: `tools/subset_fonts.py`.
- Table index: `idx = cpi/100 - 1` up to 6400 (idx 63), then 200 CPI steps:
  `idx = 63 + (cpi - 6400)/200` up to 12400 (idx 93). Verified against
  `DPIStageValue` (4/9/0x13/0x1D/0x3D = 500/1000/2000/3000/6200) and a 2 px
  sweep of the original slider.
- Thumb top y = round(425.298 - 1.8246 * idx).
- Port additions: mouse wheel over a slider/value = one table step
  (Shift = 10 steps); click the value to type an exact CPI (snapped to the
  table); value bubble while hovering/dragging.

## General page

- Sliders (min..max): acceleration 1..4, pointer speed 1..20, double-click
  1..10 (thumb positions counted on the original), scroll 1..20 (original
  mapping is non-linear; estimated). Wheel = one step (port addition).
- Polling rate 125/250/500/1000 Hz, default 500.
- Buttons 1-11 open the original popup menu: click, menu, middle, forward,
  back, keyboard key, key combo, editing / advanced / multimedia submenus,
  macro (manager + saved macros), fire key, DPI switch / + / -, profile
  switch, polling +/-, light toggle, disabled; buttons 10-11 also offer
  scroll up/down. Rule kept from the original: at least one button must stay
  "click" (WARNING 2).
- The original menu can hang below the window; the port keeps it inside.

## Lighting page

Eight modes (breathing, neon, static, wave, trail, reactive, flash, off) with
the widgets each mode showed: colour swatches + picker (breathing, static,
flash), brightness low/mid/high, speed low/mid/high (breathing, neon, wave,
flash). Swatches: ff0000 ff6600 ffff00 00ff00 00ffff 0000ff ac00cb.

## Macro manager

Same features as the original: 15 macros; new / delete; record / stop;
options record delays, default delay (ms), loop count 1-255, repeat while
held, repeat until pressed again; record key (insert), delete, move up/down,
copy, cut, paste, more... (left/right/middle click); load/save `.MSMACRO`.
Port additions: "insert delay"; double-click a delay row to type exact ms;
wheel over a delay row = +-1 ms (Shift 10, Ctrl 100); wheel on the option
boxes; keyboard shortcuts (Del, Ctrl+C/X/V, Ctrl+Up/Down); scrolling for long
macros; the name list and the totals update (the original did not repaint
them until reopened).
Recording happens while the window has focus (Wayland gives no global key hook).

## Files

`~/.config/m801-rgb/M801-RGB Gaming Mouse/RSProfile1-5.pfd` and
`MacroDB/MacroSet.MSDB` + `<name>.MSMACRO`, INI files laid out like the
original's. `DPIStageValue` uses the original encoding; other keys are the
port's own (the original's binary per-button blobs are not decoded).

## Device protocol (Holtek 04d9:fc58, verified on the user's mouse 2026-11-04)

Recorded by proxying the original driver's HID.DLL calls under Wine
(`tools/re/hix.c`: hid.exe -> HidDevice.dll -> "HIX.DLL" logger), no
encryption. Config interface = hidraw node whose report descriptor has vendor
page 0xffa0; feature report 2 = 16 bytes (8 data), 3 = 64 bytes (56 data).

| packet | meaning |
|---|---|
| `02 f5 00` / `02 f5 01` | open / close session |
| `ID f2 LO HI LEN` then GET | read; reply `ID 08 LO&~1 60+HI LEN 00 fa fa DATA` (data starts at the requested address) |
| `ID f3 LO HI LEN 00 00 00 DATA` | write |
| `02 f1 02 MASK` | commit (0x01 profile, 0x02 global, 0x04 buttons, 0x10 dpi) |

Memory map: 0x2c active profile; 0x32+2p report interval ms (1/2/4/8 =
1000/500/250/125 Hz, applied only after USB re-enumeration -> the port issues
USBDEVFS_RESET itself); profile bases 0x40, 0x100, 0x1b0, 0x260, 0x310: base+2
current DPI stage, base+4 five stages `[on][X u16][Y u16][00]`, base+0x42 nine
buttons x 4 bytes, base+0x9a / base+0x9e wheel up / down.

Lighting (verified visually): 0x449+8p = `[R][G][B][mode][b4][b5][brightness]`,
mode 01 breathing, 02 neon, 03 static, 04 flash, 05 wave, 06 spectrum/trail,
07 reactive (lights on movement), 08 off; brightness 1-3 (0 = dark). Applied
live. b4 = effect speed (smaller = faster; the port uses 8/4/1 for
low/mid/high, verified on breathing); b5 and a "colour changes on click"
behaviour in static mode are not decoded (b5 kept as the device holds it).

Macros (verified with an F13 test macro): 15 slots of 200 bytes at
0x478 + 200*slot; events of 3 bytes `[type][code][hi]`, zero terminated:
0x84/0x04 key down/up (HID usage), 0x81/0x01 mouse button down/up
(01 left, 02 right, 04 middle), 0x06 delay in 10 ms units (u16 LE).
Button binding `91 SLOT LOOPS MODE`: MODE 00 = play LOOPS times,
01 = repeat until pressed again; "repeat while held" was not found (02 also
keeps repeating), so the port stores it as a loop.

DPI register = table from hid.exe (`DPI_TABLE`, 100-6200 CPI); above 6200:
`0x100 | table[cpi/2]` (8000 -> 0x15a, 11800 -> 0x185).

Button codes: the original driver's own table, extracted from hid.exe
(@0x47e3c0, pfd ButtonFunc id -> 4 bytes) with Ghidra 11.3.2
(`tools/re/DecompileAll.java`, headless) plus its special cases in
FUN_00413990. Menu ids from ldcfg.exe: 17-24 Editing, 25-38 Advanced,
39-46 Media, 47-49 DPI, 50-51 polling, 52-54 wheel up/down + light toggle.

| function | bytes |
|---|---|
| left / right / middle | 81 / 82 / 83 |
| forward / back | 85 / 84 |
| DPI cycle / + / - | 88 / 8a / 89 |
| wheel up / down | 8b / 8c |
| profile switch | 8d |
| polling + / - | 97 / 98 |
| light on/off | 9b 04 |
| key | 90 00 USAGE 00 |
| combo | 8f MASK USAGE 00 (Ctrl 1, Shift 2, Alt 4, Win 8) |
| editing / advanced | 8e 01 ff 10+n / 8e 01 ff 18+n |
| media 1-7 | 8e 01 USAGE (cd b7 b6 b5 e9 ea e2) |
| fire key | 99 TARGET(81/82/84) TIMES DELAY/10 |
| macro | 91 SLOT\|0x80 (while held) or \|0x40 (until pressed again) LOOPS(u16, ffff for those two) |
| disabled | 00 |

Editing/advanced `8e 01 ff 10+n / 18+n` are software-only: the mouse sends consumer
usage 0x1fff (descriptor range 0..0xfff) and hid.exe (FUN_00411ae0) replays
keystrokes / WinExec. Linux drops the report, so Dragonize writes them as
hid.exe's keystrokes (Ctrl+X/C/V/A/F/N/P/S, Alt+Tab, Alt+F4, Win+E, Alt+F2 for
Win+R, Win+D, Win+L for LockWorkStation, F3) or standard consumer usages
(0x196 browser, 0x224-0x227 back/forward/stop/refresh, 0x22a bookmarks, 0x18a
mail); the old codes still decode (device.rs BASIC_CODES / ADVANCED_CODES).

Checked on the device: 81-85, 88-8d, 90, 8e (consumer), 98, 99, macros
(loops, 0x80 stops on release after 3.3 s, 0x40 runs between two presses),
lighting static = mode 01 + variant 02 (no colour change on click).
Lighting per hid.exe FUN_0040f7f0: tab -> (mode, variant): breathing (1,4),
neon (1,8), static (1,2), wave (2,0), trail (6,0), reactive (7,0),
flash (1,10), off (0,0); speed byte low/mid/high = 8/5/2; brightness 1-3.
Any other code is kept as `Raw` and written back unchanged.

Warning: the original program's Apply is not fully compatible with this
firmware (it zeroed a macro button and rewrote lighting bytes); the user's
configuration was restored from `reference/device/pristine_device_read.log`.

E2E (2026-11-04, port -> device -> physical check): read-back of all written
fields; buttons produced BTN_EXTRA, BTN_SIDE, keys, Ctrl+C; DPI cycle; polling
measured 1.00 / 2.00 / 8.00 ms for 1000 / 500 / 125 Hz after re-enumeration;
F13 macro timing confirmed 10 ms delay units.

## Access on other machines

`/dev/hidraw*` and the usbfs node are root-only on most distributions (the
development machine had them world-writable through another package's rule).
Host device permissions cannot be shipped inside an AppImage, so on first use
the app shows a dialog and, with the user's consent, installs
`/etc/udev/rules.d/70-dragonize.rules` through pkexec (polkit password prompt):
`TAG+="uaccess"` for the supported 04d9 product ids only (hidraw + usb), i.e. access for the
logged-in user, nothing else. Terminal equivalents: `--install-udev-rule`,
`--diagnose`. Verified: the AppImage reads/writes the mouse inside Debian 11
(glibc 2.31) and Ubuntu 24.04 containers once access is granted, and reports
"NoPermission" when it is not.

## Not implemented

- MEDIA 8 "player" (no code in the original table).
- Tray icon.

Apply / OK: writes the changed fields, verifies by read-back, then always
re-enumerates the mouse (USBDEVFS_RESET) and reopens it (the hidraw node may
change); a stale handle after an unplug/replug is reopened on the next Apply.
Apply runs in a worker thread while a "saving" screen in the dialog style
shows the phase (reading / writing / reconnecting); it closes when the mouse
is back. `m801-rgb --device-apply` runs the same path headless (~4 s).
Editing a DPI stage value also makes it the active stage (a change to an
inactive stage has no visible effect, which read as "DPI not applied").
Measured on the device: 200 CPI -> 777 counts/s, 12400 CPI -> 8357 counts/s
with normal hand movement (both values take effect).
The preset colour in use is marked with the original's check mark.

Safety check: `m801-rgb --device-roundtrip` reads the mouse, converts it to the
app model and back, and must report no difference (Apply without changes
writes nothing). It passes on the user's mouse.
